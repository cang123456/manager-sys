这个问题值得讲清楚。我先画一张图，因为只看文字很难理解这条链路。
## 一句话概括

它是一条 **“浏览器 → 代理 → 大模型 → 浏览器”的 SSE 回流链路**，本质上是把 OpenAI 的 function calling 协议接到若依的路由上。

## 分层列出

| 层             | 技术                                | 具体用法                                                     |
| -------------- | ----------------------------------- | ------------------------------------------------------------ |
| **UI**         | Vue 3.5 + `<script setup>`          | 悬浮球、抽屉、打字机、JSON 折叠区全部手写；**没有引入任何 chat/UI 组件库**，样式直接使用你项目里的 `--ap-*` 主题变量 |
| **流式接收**   | 原生 `fetch` + `ReadableStream`     | 手工分帧 `event:` / `data:`，累加 `tool_calls` 分片          |
| **前端工具层** | 纯 JS 注册表                        | `utils/aiTools.js`：`schema`（给模型看）+ `handler`（浏览器执行）+ 菜单清单生成 |
| **代理**       | Vite 6.4 dev proxy                  | `/dev-api` → `localhost:8080`，复用项目已有配置              |
| **后端**       | Spring Boot 3.5.16 / JDK 17         | `SseEmitter` 做流式出口，**Servlet 栈，不是 WebFlux**        |
| **上游调用**   | JDK 自带 `java.net.http.HttpClient` | `sendAsync` + `InputStream`，逐行读 `data:` 再原样转发       |
| **鉴权**       | 若依原有 Spring Security + JWT      | 前端带 `Bearer`，后端不加白名单                              |
| **模型**       | 阿里云百炼 DashScope                | OpenAI 兼容端点，`tools` / `tool_calls`，当前 `gui-plus`     |

**关键数字：后端新增 0 个 Maven 依赖，前端新增 0 个 npm 依赖。** 这是刻意的：`HttpClient` 和 `fetch` 都是标准库自带的。

## 四个“为什么不用 X”，这才是有价值的部分

**1. 为什么不用 LangChain / LangChain4j / Spring AI**
这条链路只有两件事：转发字节、拼接分片。而**工具的真正执行在浏览器**，也就是跳路由。你不可能用 Java 去 `router.push`。在 Java 侧套一层 LangChain，只会多一层黑盒：出问题时，你不知道是框架的 agent 循环、还是提示词、还是网络层。最小闭环就该没有框架。

**2. 为什么用 SSE 不用 WebSocket**
数据是**单向**的：用户发一句，模型回一段。WebSocket 是双向长连接，若依的 JWT 鉴权还得另做一套握手逻辑；SSE 就是普通 HTTP 响应，`Authorization` 头照常生效，现有安全配置一行不用改。

**3. 为什么不用浏览器原生的 `EventSource`**
这个坑很具体：`EventSource` **只能发 GET，且不能自定义请求头**。而我们的请求要 POST 带 body（messages + tools）、还要带 `Authorization`。所以只能用 `fetch` 自己读流、自己分帧。

**4. 为什么不用 axios**
axios 在浏览器端底层是 XHR，**拿不到 `ReadableStream`**，做不了逐字输出。这是“库的能力边界”问题，不是喜好问题。

## 在这套栈里，哪些东西只能靠设计解决

模型并不知道你的系统里有什么。所以真正让功能可以运行的，是**请求里塞进去的那份菜单清单**：从 `router.getRoutes()` 取当前账号真实可访问的路径，拼进 system message。

这不是技术栈，是**协议设计**。也是我踩过的坑：不给清单，`gui-plus` 直接编了个 `userManage`。

---

你现在这套东西的边界也很清楚：**它只能做“浏览器里能做的事”**（跳路由、开弹窗、改主题）。如果要让 AI 查数据库、调后端接口，那就得在后端加工具、把 `tools` 的执行权拿到服务端；那是功能点2 的架构，跟现在这套不一样。
