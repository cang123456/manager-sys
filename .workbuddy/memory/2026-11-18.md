## Redis「总是启动不了」诊断（E:\soft\Redis\Redis-8.10.1-Windows-x64-cygwin-with-Service）

结论：**Redis 本身没坏，能正常启动**。日志 `redis.log` 显示今天 08:12 / 08:13 / 08:17 三次 `Ready to accept connections tcp`，每次都成功。

### 真正的原因
1. `redis.conf` 中 `daemonize no` + `start.bat` 用 `redis-server.exe redis.conf` 前台启动 → **关掉黑窗口进程就没了**，下次打开自然像“启动不了”。这是 cygwin 版最常见的困惑。
2. 今早 08:11 用户把 `redis.conf` 从完整示例 `redis.conf.exaple`（129KB）重写成 1743 字节精简版，并加了 `requirepass 123456`；但后端 `RuoYi-Vue-springboot3/ruoyi-admin/src/main/resources/application.yml` 的 `spring.data.redis.password:` 仍是**空** → 即使 Redis 在跑，后端也会 `NOAUTH` 认证失败。
3. 残留 pid 文件：`redis.pid`（1466→1348）、`redis_6379.pid`（426），是多次前台启动/强关留下的，可能造成误判。

### 实测
- `redis-server.exe redis.conf --daemonize yes` 启动成功，`redis-cli -a 123456 PING` 返回 `PONG`，端口 6379 LISTENING。
- 但工具会话结束时进程被环境清理（日志无正常 shutdown 记录，pid 1348 直接消失），**AI 工具无法替用户维持常驻后台服务**。用户需自己在终端启动，或装成 Windows 服务。
- `sc.exe` 被 WorkBuddy 安全策略列入程序黑名单，不要再用它查服务。

### 推荐方案（已告知用户，待其选择）
- 一劳永逸：`RedisService.exe install -c <绝对路径>\redis.conf --dir <数据目录> --port 6379`，再 `net start Redis`（需管理员权限，用户自己执行）。
- 或把 `daemonize no` 改成 `yes`，`start.bat` 里加 `redis-cli -a 123456 shutdown` 之类管理命令。
- 密码二选一：Redis 保留 `requirepass 123456` 则后端 `application.yml` 要填 `password: 123456`；否则删掉 `requirepass`。

### 浏览器实测暴露的两个 bug（已修，11:38~11:55）
1. **Spring Security 会拦截 SSE 的 ASYNC 分派** → `AuthorizationDeniedException: Access Denied`，此时响应已 committed，Tomcat 只能掐断连接，前端表现为 `Connection reset`。
   修：`ruoyi-framework/.../SecurityConfig.java` 的 `authorizeHttpRequests` 里加
   `requests.dispatcherTypeMatchers(DispatcherType.ASYNC, DispatcherType.ERROR).permitAll();`（影响全站异步接口，非只 AI）。
2. **`BodyHandlers.ofLines()` 在流式场景不稳**（阻塞迭代器，网关断流时抛裸 SocketException，堆栈指不到位置）。
   修：改 `ofInputStream()` + `BufferedReader.readLine()`，并 `HttpClient.version(HTTP_1_1)`。

### 「点停止主动取消上游」（用户要求，已实现并实测）
- 用 `sendAsync` + `CompletableFuture`，持 `InputStream` 引用；`onCompletion/onTimeout/onError` 三个回调统一走取消（`AtomicBoolean` 幂等）。
- 关键坑：**Windows 上 Tomcat 写回已断开的连接抛的是 `IOException`（WSAECONNABORTED），不是 `IllegalStateException`**。原来它掉进兜底 catch 被当成“百炼故障”，取消逻辑永远不执行。现在把 `emitter.send` 包成 `sendEvent()`，任何失败转 `ClientGoneException` 单独处理。
- 用 `AtomicBoolean normalFinish` 区分「自己 complete」和「前端断开」，避免正常收尾也打“前端已断开”。
- 实测：长文本请求 2 秒中途掐断 → 日志出现「前端已断开，已取消上游请求」→ 紧接着的新请求 2 秒正常返回 6 分片。
